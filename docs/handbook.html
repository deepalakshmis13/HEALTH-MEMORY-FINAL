01

The problem, and the insight underneath it

An elderly patient in India typically sees a cardiologist at one hospital, a physician at a neighbourhood clinic, buys medicines from a pharmacy that keeps no record, and is cared for daily by a family member or a facility attendant who has never met either doctor. Their health story exists — it is simply scattered across people who never speak to each other.

The cost of that scattering is not inconvenience. It is a doctor prescribing without knowing what a different doctor changed three weeks ago. It is a caregiver administering a dose that was misread off a handwritten slip. It is a paramedic with no idea what the patient is allergic to.

The obvious response is "build an EHR". That has been tried, and it fails for this population for a structural reason: an EHR belongs to an institution. An elderly patient's care does not happen inside one institution.

The insight this project is built on. The record should follow the patient, not the clinic — and the moment a record leaves an institution, two problems that an EHR never had to solve become the whole problem: who is allowed to see which part of it, and how much do we trust each fact in it. Everything in this system is an answer to those two questions.

That is why the chatbots are not the product. A language model over a pile of medical text is easy and dangerous. The product is the memory layer underneath: persistent, provenance-carrying, consent-gated, and human-verified where it matters. The four AI agents are interfaces onto that layer — and they can only ever see what the layer has already decided they may see.

02

What the system is

A web platform where an elderly patient (or their guardian) builds a single, permanent health memory from three kinds of input — typed text, spoken voice, and scanned or photographed documents including handwritten prescriptions — and then decides, scope by scope, which of the people caring for them may read which part of it.

Role 01

Patient / Guardian

Adds information, sees a plain-language timeline, controls consent, keeps an Emergency Health Card, and asks an assistant that answers in everyday words.

Role 02

Doctor

Receives records routed from documents that name them, reads a longitudinal clinical timeline, and generates a one-click visit summary they review and save.

Role 03

Caregiver / Old Age Home

Runs shift-based medication rounds and care tasks, records observations, and generates an evidence-backed handover for the next shift.

Role 04

Pharmacist

Works a verification queue containing only the medication details that were read below the confidence threshold, with the original page beside the reading.

One record, four working surfaces. A caregiver and a cardiologist looking at the same patient are reading the same underlying memory events — filtered differently, labelled identically.
03

Four things that make this different

Differentiator 1 · Handwriting is a first-class input, not a failure case

Most document pipelines treat a handwritten prescription as a bad scan. Here it has its own recognition engine, its own confidence calibration, and its own downstream consequence. OCR of cursive medical script returns things like Amlod!pine — so medication extraction matches approximately against a drug lexicon and lowers its confidence by the similarity gap, keeping the raw reading so a human can see what was actually on the page.

Differentiator 2 · Uncertainty is routed to a human, selectively

Every extracted field carries its own score. A field goes to a pharmacist only when it is both below the auto-accept threshold and clinically important. A doctor's name read at 66% does not interrupt anybody. A dose read at 66% does. That rule is written once, in one function, and is the reason the queue stays workable instead of becoming a firehose.

Differentiator 3 · Consent is a retrieval filter, not a UI toggle

Unauthorised records are removed from the candidate set before relevance is scored. The language model is never handed something it is asked to ignore. Revoke "Recent History" from doctors and consultations disappear from the timeline, the visit summary and the chatbot in the same instant — because all three read through the same filter.

Differentiator 4 · Provenance survives every transformation

A pharmacist correcting Amlodipne to Amlodipine does not overwrite anything. The original OCR string, its original confidence, the corrected value, the pharmacist's name and the timestamp all persist together. Six months later the record still says where the fact came from and who vouched for it.

The safety property that follows from all four: a caregiver cannot record an unverified medication as administered. The API returns 409 Conflict — it is enforced in the backend, not warned about in the interface.
04

The pipeline

Every piece of information, whatever its origin, travels the same eight stages. The stages are ordered deliberately: nothing becomes retrievable before its trust level has been established.

01CaptureText typed · voice spoken · document scanned
02RecognitionSpeech-to-text in the browser · PrintedOCR or HandwritingOCR on the server
03ExtractionLexicon + regex entity extraction with fuzzy drug matching
04Confidence analysisPer-field score, band, clinical-importance flag
05Routing decision≥ 85% accepted · below threshold and clinically important → pharmacist queue
06Health memory writeMemoryEvent + structured rows, provenance attached
07IndexChunked, embedded, metadata-tagged into the RAG store
08Consent-filtered retrievalRole agent composes an answer with its evidence
Priority order, as designed: persistence → provenance → OCR confidence → human verification → consent → authorization → retrieval → role-specific AI → evidence-backed response. Read left to right, each stage is a precondition for the next.

config.py — the single source of truth

Every tunable value in the system lives in this one file, and every one of them can be overridden by an environment variable without touching code. This matters for a specific reason: the confidence thresholds are the ethical centre of the system, and they must be auditable in one place rather than scattered through the codebase.

Application

APP_VERSION1.0.0Reported by /api/health and /api/system/config.
DATABASE_URLsqlite:///…Any SQLAlchemy URL. Point it at postgresql+psycopg://… and nothing else changes.
STORAGE_DIR./storageWhere uploaded documents land, under a patient_<id>/ subfolder. Created at import time.
CORS_ORIGINS3 originsComma-separated. Defaults cover the Vite dev server and preview server.

Security

SECRET_KEYdev-only…HMAC key for token signatures. Must be replaced before any deployment — a known key means forgeable sessions.
TOKEN_TTL_SECONDS4320012 hours. Raising it lengthens the window in which a stolen token is usable; lowering it forces re-login mid-shift, which is why 12h was chosen for a care setting.
PASSWORD_HASH_ITERATIONS120000PBKDF2-SHA256 rounds. Higher is safer and slower — roughly linear cost on login. Not environment-overridable by design: lowering it should require a code change and review.
MAX_UPLOAD_BYTES1572864015 MB. A phone photograph of a prescription is typically 2–5 MB, so this leaves headroom without inviting abuse.
ALLOWED_UPLOAD_EXTENSIONS9 types.pdf .png .jpg .jpeg .webp .tif .tiff .txt .doc .docx — checked before the file is written to disk.

Confidence thresholds the ethical centre

HIGH_CONFIDENCE_THRESHOLD0.85At or above this, an extracted field is accepted straight into health memory with its provenance. Raise it and more work reaches the pharmacist (safer, slower). Lower it and more uncertain data is trusted automatically (faster, riskier).
MEDIUM_CONFIDENCE_THRESHOLD0.60The boundary between a NORMAL and a HIGH priority verification task. It changes queue ordering and urgency, never whether a task exists.
CLINICALLY_IMPORTANT_FIELDS7 fieldsmedication_name · medication_dose · medication_frequency · prescription_instruction · medication_change · allergy · critical_instruction. This set is the second half of the routing rule — a field outside it never creates a task, however badly it was read.

Retrieval

RAG_CHUNK_SIZE480Characters per chunk, with sentence-boundary snapping. Smaller chunks sharpen precision and fragment context; larger ones do the reverse. 480 fits a single consultation note or medication event whole.
RAG_CHUNK_OVERLAP60Characters carried into the next chunk so a fact spanning a boundary is not lost.
RAG_TOP_K8Chunks passed to the agent. Raising it broadens context and dilutes relevance; the context builder also caps total context at 6,000 characters, so very large top_k is silently truncated.
RAG_RECENCY_HALFLIFE_DAYS120A record 120 days old scores half the recency of one from today. Shorten it for acute care where last week is all that matters; lengthen it for chronic elderly care where a two-year-old diagnosis is still live. 120 days is a deliberate middle for this population.
EMBEDDING_DIM256Hash buckets in the embedding vector. Higher reduces collisions at the cost of storage per chunk; 256 is ample for a per-patient corpus of a few hundred chunks.

AI provider

AI_PROVIDERautoauto uses the hosted model if a key is present, else the mock. mock forces deterministic grounded output. llm forces the API and falls back to the grounded draft on any error.
LLM_API_KEYunsetThe only value in the system whose absence changes behaviour rather than causing an error.
LLM_MODELclaude-sonnet-4-5Used only when a key is configured.

Authentication and authorization

Password hashing — utils/security.py

PBKDF2-HMAC-SHA256, 120,000 iterations, a fresh 16-byte salt per user, compared with hmac.compare_digest so verification is constant-time. Stored as a single self-describing string:

pbkdf2_sha256$120000$<salt-hex>$<digest-hex>

The iteration count travels with the hash, so raising it later does not invalidate existing passwords.

Tokens

A compact JWT-shaped token built from the standard library only — no third-party JWT dependency to pin or patch:

# payload
{ "sub": user_id, "role": role, "email": email,
  "iat": issued, "exp": issued + 43200, "jti": random_hex }

# wire format
base64url(payload) . base64url(HMAC-SHA256(payload, SECRET_KEY))

Verification recomputes the HMAC, compares it constant-time, then checks exp. A tampered payload fails the signature; an expired one fails the clock.

The three-layer access check

L1Authenticationget_current_user() resolves the bearer token into a Principal — user plus role profile.
L2Role guardrequire_roles("pharmacist") rejects wrong-role callers at the route boundary.
L3Patient-level authorizationrequire_patient_access() resolves the actual care relationship and returns an AccessContext carrying the granted consent scopes.

Layer three is what stops a legitimately-signed-in doctor reading a patient they have no relationship with. relationship_reason() answers the question per role:

RoleAccess granted whenReason string shown in the UI
PatientIt is their own recordOwn health record
DoctorPrimary doctor, or an assignment existsPrimary doctor / Treating doctor / Routed from a medical record
CaregiverAssigned, or same facility in old-age-home modeAssigned caregiver / Resident of the same care facility
PharmacistMedication consent granted, or queue work existsMedication verification and dispensing
A refused access attempt writes an ACCESS_DENIED audit event before returning 403. Denials are evidence, not silence.

The OCR subsystem

Three files: an engine router, two engines, and the scoring module that decides what happens to what they read.

Handwriting detection — three signals, in order

PrioritySignalMechanism
1Explicit declarationThe uploader ticked "handwritten by the doctor". Always wins.
2Filename hints13 substrings: handwritten, scribble, doctor_note, rx_, …
3Ink-distribution heuristicDownsamples to 320×320, measures per-row dark-pixel density. Printed text has dense, regular rows; handwriting is sparse and uneven. Score min(1, variance×45 + max(0, 0.55 − coverage)); ≥ 0.35 means handwriting.

The two engines

Engine

PrintedOCR

Native .txt read at 0.99. Embedded PDF text at 0.97. Otherwise Tesseract via image_to_data, mean word confidence clamped to 0.35–0.99.

Engine

HandwritingOCR

Tesseract with --psm 6, then a calibration multiplier of ×0.82 clamped to 0.30–0.93 — because recognisers are systematically over-confident on cursive medical script.

Demo mode. With no Tesseract installed, both engines degrade a known text deterministically — dropping strokes and applying a real confusion map (i↔l, o↔0, 5↔s, n↔m) — and report a confidence to match. Handwriting legibility ranges 0.42–0.78, printed 0.88–0.98. The rest of the pipeline is identical, so the demo behaves correctly on any machine.

Per-field confidence offsets

The document's recognition confidence is the baseline; each field is adjusted by how reliably that kind of value can be read. A frequency abbreviation is harder to read correctly than a printed doctor's name — so it carries a penalty.

FieldOffsetRationale
doctor_name+0.03Usually on a printed letterhead even when the body is handwritten.
medication_name+0.04 − penaltyLexicon-anchored, so a match is meaningful — minus (1 − similarity) × 1.3 for a fuzzy match.
medication_dose−0.01 / −0.02Numerals and units are comparatively legible.
consultation_date−0.02Digits, but ambiguous formats.
vitals−0.02Structured pattern (148/92).
diagnosis, lab_result−0.03Lexicon-matched free text.
symptom−0.04Free text, wide vocabulary.
allergy, prescription_instruction−0.05Free text after a trigger phrase.
medication_change−0.06Inferred from surrounding verbs, not stated.
critical_instruction−0.07Regex-captured clause; boundaries are uncertain.
medication_frequency−0.08 / −0.09The largest penalty. OD, BD, TDS, HS are short, similar and consequential — the most dangerous thing to misread on a prescription.

The RAG subsystem

Chunking — rag/chunker.py

Text is split at 480 characters with 60 characters of overlap, snapping backwards to a sentence or line boundary where one falls in the second half of the window. The event title is prepended to the first chunk so a chunk is self-describing. Re-indexing a source deletes its old chunks first, so an update never leaves a stale copy behind — which is exactly what happens when a pharmacist corrects a reading.

Embeddings — rag/embeddings.py

A 256-dimension hashed bag-of-words vector, L2-normalised so cosine similarity is a dot product. Three feature families are hashed into the same space:

whole tokensweight 1.0Stopword-filtered, minimum 2 characters. Weight 1.6 if the token is in the 30-word medical boost list (medication, dose, allergy, verified, handover, …).
character 4-gramsweight 0.45Why the system tolerates OCR noise. Amlodipme and Amlodipine share most of their 4-grams, so they land close together in vector space even though no whole token matches.
adjacent bigramsweight 0.6Preserves a little word order — blood pressure is not the same as pressure blood.
Swapping in a hosted embedding model means replacing one function, embed(). The retriever depends on nothing else in this file.

Retrieval — the seven ordered stages

1Patient isolationWHERE patient_id = ? — the first line of the query, always.
2AuthenticationHandled by the route dependency before the retriever is reached.
3Role source policyCaregivers and pharmacists see only their permitted source types; patients and doctors see all consented sources.
4Consent restrictionChunk's consent_scope must be in the viewer's granted scopes. Caregivers are additionally blocked from VOICE_DIARY.
5Verification statusREJECTED chunks are removed from the candidate set entirely.
6RelevanceSemantic and lexical scoring — the first stage that looks at the question at all.
7RecencyExponential decay applied to the final ranking.
Stages 1–5 run before stage 6. That ordering is the security property: unauthorised records are gone from the candidate set before anything is scored, so the language model is never handed a record it is asked to ignore. Prompt-level instructions to "not use" a record are not a security boundary; a filter is.

Context building — rag/context_builder.py

Retrieved chunks become a labelled block, capped at 6,000 characters. Every chunk carries its provenance inline, so the model physically cannot present an unverified reading as fact without contradicting the text in front of it:

[3] Medication: Amlodipine — 5 mg — Once daily — 12 Aug 2026
    provenance: OCR Extracted | UNVERIFIED — pending pharmacist verification | confidence 54% | recorded by Radha Krishnan
    Amlodipine 5 mg once daily. Instruction: After Food.

The same source list is returned to the interface and rendered as the "Why am I seeing this?" evidence panel under every answer.

Agents and the AI provider

MemoryAgent — the shared reasoning layer

Never talks to a model. It classifies intent across 15 categories by weighted keyword match — medications, medication_changes, last_visit, verification, shift, watch, due, labs, observations, emergency and others — runs the consent-aware retrieval, and hands the role agent a bundle of facts that demonstrably exist.

The four role agents

AgentRoleRegister enforced by its system prompt
My Health Memory AssistantPatientShort sentences, everyday words, no jargon unexplained, never advises a dose change, always says when something is awaiting verification.
Clinical Health Memory AssistantDoctorConcise clinical register with headings; separates doctor-recorded, pharmacist-verified, OCR-pending, caregiver-observed and patient-reported explicitly.
Care CompanionCaregiverLeads with what must be done and watched; never authorises a dose change; always names what to escalate.
Medication Memory AssistantPharmacistPrecise about readings and scores; quotes the original OCR text beside any corrected value; never guesses an illegible reading.

The provider abstraction — why the mock is not a stub

Each role agent composes a grounded draft directly from the retrieved records — real medication names, real dates, real verification statuses. Both providers receive the same three things: a system prompt, the consent-filtered context, and that draft.

No API key

MockAIProvider

Returns the grounded draft as the answer. It is not filler — it is assembled from the patient's actual records, which is why every demo question produces a correct, specific, evidence-backed answer with no network at all.

With LLM_API_KEY

LLMProvider

Sends prompt + context + draft to the model with instructions to rewrite in the role's register and add no clinical fact not already present. Any error — network, timeout, empty response — falls back to the grounded draft.

The consequence worth stating in a pitch: the language model is an optional presentation layer. Remove it entirely and the system still answers every question correctly. That is the opposite of the usual demo, where removing the model leaves nothing.

Master parameter reference

Every value that changes system behaviour, what it does, and what moving it costs you. This is the table to have open when someone asks "why 0.85?"

ParameterDefaultEffect of raisingEffect of lowering
HIGH_CONFIDENCE_THRESHOLD0.85 More fields flagged → safer, larger pharmacist workload. At 0.95 nearly every handwritten field queues. More auto-accepted → faster, riskier. At 0.50 a misread dose enters memory unchallenged.
MEDIUM_CONFIDENCE_THRESHOLD0.60 More tasks marked HIGH priority; the urgent list loses its meaning if everything is urgent. Fewer HIGH tasks; genuinely illegible readings lose their visual urgency.
CLINICALLY_IMPORTANT_FIELDS7 fields Adding diagnosis or lab_result would roughly double queue volume. Removing medication_frequency would let "once daily" vs "four times daily" pass unchecked. Do not.
RAG_TOP_K8 Broader context, more dilution, longer prompts. Capped in practice by the 6,000-character context limit. Sharper but risks missing a relevant older record.
RAG_CHUNK_SIZE480 More context per chunk, coarser matching. Finer matching, more fragments, higher chance of splitting a dose from its drug.
RAG_CHUNK_OVERLAP60 Better boundary coverage, more duplicate text in the index. Leaner index; a fact split across a boundary may match neither chunk.
RAG_RECENCY_HALFLIFE_DAYS120 Older records stay competitive — right for chronic conditions. Strong recency bias — right for acute care, wrong for a stable elderly patient.
EMBEDDING_DIM256 Fewer hash collisions, more storage per chunk. More collisions and false matches. Below ~128 quality degrades noticeably.
Semantic / lexical split0.62 / 0.38 More semantic → better paraphrase handling, worse exact drug-name matching. More lexical → better exact matching, worse on questions worded differently from the record.
Relevance / recency / trust0.60 / 0.22 / 0.18 More trust weight → verified records dominate and recent unverified ones get buried. Less trust weight → unverified OCR competes on equal footing with confirmed data.
Handwriting calibration×0.82 Toward 1.0 trusts Tesseract's own confidence — which is measurably optimistic on cursive. Below 0.7 floods the queue with fields that were actually read correctly.
Fuzzy match threshold0.80 Fewer false drug matches, more missed ones on badly degraded text. Catches more OCR noise but risks matching an unrelated drug — dangerous below ~0.75.
Fuzzy match penalty×1.3 Approximate matches score lower → more of them queue for a human. Approximate matches are trusted more readily.
TOKEN_TTL_SECONDS43200 Fewer interruptions, longer exposure if a token leaks. Tighter security, re-login mid-shift.
PASSWORD_HASH_ITERATIONS120000 Harder to brute-force, slower login (roughly linear). Faster login, weaker against offline cracking.

Confidence maths, worked

The routing rule

Written once, in ocr/confidence.py:

def needs_verification(field):
    return (
        field["confidence"] < HIGH_CONFIDENCE_THRESHOLD
        and field["field"] in CLINICALLY_IMPORTANT_FIELDS
    )
Band

HIGH ≥ 0.85

Accepted into health memory. Provenance still recorded.

Band

MEDIUM 0.60 – 0.84

"Needs Verification" — NORMAL priority, if the field is clinically important.

Band

LOW < 0.60

"High Priority Verification" — HIGH priority, if the field is clinically important.

Document score — overall_confidence()

A document's score is not a plain average. Clinically important fields are weighted double, and then the weakest important field pulls the whole document down — because a prescription is only as trustworthy as its least legible dose.

mean = Σ(confidence × weight) / Σ(weight)     # weight = 2.0 if important else 1.0
mean = min(mean, (mean + min_important_score) / 2 + 0.02)

Worked example — the seeded handwritten prescription

A real run against Doctor_Handwritten_Note.png, read by Tesseract at a recognition confidence of 0.54:

medication_nameAtorvastatin67%YesNORMAL task

Read the doctor's name row. At 66% it is less confident than Atorvastatin at 67%, and it is still accepted — because it is not in CLINICALLY_IMPORTANT_FIELDS. That single row is the clearest demonstration of the rule: the system routes by consequence, not by score alone.

For contrast, the seeded printed lab report scores 89% and the discharge summary 90% — both above threshold, both creating zero pharmacist tasks. The second handwritten prescription lands at 62%, producing a NORMAL-priority task rather than a HIGH one. All three bands are demonstrable from the seeded data alone.

Retrieval scoring, worked

semantic  = cosine(embed(question), chunk.vector)
lexical   = keyword_overlap(question, chunk.title + chunk.text)

relevance = semantic × 0.62  +  lexical × 0.38
recency   = 0.5 ^ (age_days / 120)
trust     = trust_score(chunk)

score     = relevance × 0.60  +  recency × 0.22  +  trust × 0.18

The trust score

Verification statusBaseMeaning
VERIFIED / CORRECTED1.00A pharmacist has vouched for it.
NOT_REQUIRED0.90Above threshold, or not clinically critical.
PENDING_VERIFICATION0.45Retrievable but heavily demoted — and always labelled.
REJECTED0.05Never reaches scoring; filtered out at stage 5.

An additional penalty applies to anything below the high-confidence threshold that has not been verified:

if confidence < 0.85 and status not in {VERIFIED, CORRECTED}:
    base ×= 0.75 + (confidence × 0.25)

So a pending field read at 54% ends at 0.45 × (0.75 + 0.135) ≈ 0.398 — roughly 40% of the trust of a verified record. It stays findable; it simply cannot outrank confirmed information.

Recency in practice. Today 1.00 · 30 days 0.84 · 120 days 0.50 · 1 year 0.12 · 2 years 0.015. A two-year-old record is not excluded — it just needs strong relevance to surface, which is the correct behaviour for a chronic diagnosis.
The vague-question fallback. If every top-k result scores relevance below 0.08, the retriever discards the ranking and returns the most recent authorised chunks instead. "How am I doing?" gets recent context rather than eight arbitrary near-misses.

Flow: pharmacist verification

The pharmacist opens a task and sees five things at once: the original page, the OCR text, the confidence with its band explained, every field extracted from that document, and the patient's existing medications and allergies — the last of these consent-checked before it is shown.

Action

Verify

The reading was right. Status → VERIFIED, memory event promoted to Pharmacist Verified at confidence 1.0.

Action

Correct

The reading was wrong. Status → CORRECTED. The structured medication row is updated; the original OCR value and score are preserved in extra.

Action

Reject

Illegible — a reason is required. Status → REJECTED; the chunk is excluded from all retrieval but stays in the record for audit.

What _finish() writes on a correction, in one transaction:

  1. A VerificationResult row with the original value, the original confidence, the corrected value, the clarification, the pharmacist and the timestamp.
  2. The Medication row updated to the corrected value, source_type → PHARMACIST_VERIFIED, confidence → 1.0.
  3. The MemoryEvent content rewritten with a bracketed provenance note, trust level → Pharmacist Verified, and the full correction history stored in extra.
  4. The event re-indexed — the stale chunk is deleted and replaced, so retrieval immediately reflects the correction.
  5. The parent document's status recomputed: still PENDING_VERIFICATION if other tasks remain on it.
  6. A VERIFICATION_CORRECT audit event recording the before and after.
Nothing is overwritten and nothing is lost. The timeline card for that medication now shows: Original OCR "Amlodipne" at 54% → corrected to Amlodipine by Kavitha Menon. That line is the whole trust argument of the project, rendered from data.

Flow: visit summary and shift handover

One-click visit summary

Eleven sections, each built from a real query, not from a prompt: patient overview · recent clinical history · current medications · recent medication changes · lab results · hospital visits · patient-reported information · caregiver observations · important alerts · unresolved issues · suggested questions.

"Unresolved issues" is assembled from pending verification tasks and missed medication doses. "Suggested questions" is derived from what actually changed — a recent medication change produces a tolerance question; an abnormal lab produces a review question.

The draft is never the record. Every summary opens with an explicit AI-GENERATED DRAFT banner and is stored as DRAFT. Only when the doctor edits and saves does it become a memory event — and it is then stamped DOCTOR_RECORDED with origin: "AI draft reviewed and saved by the doctor" in extra. The audit trail distinguishes generation from acceptance.

Shift handover

Per patient, eight sections: patient status · medication administered · missed or delayed · new observations · important changes · pending tasks · alerts · next-shift instructions.

The instructions are generated conditionally from shift state. A missed dose produces an escalation instruction. A flagged observation produces a monitoring instruction. An unverified medication produces an explicit "do not administer" line naming the drug. When nothing needs attention, it says so rather than inventing filler.

Saving writes an OBSERVATION memory event to every patient in the shift, so the next caregiver, the doctor and the patient all see the same handover.

Question bank

Isn't this just a chatbot over a database?
The opposite. Remove the language model entirely and every question is still answered correctly, because the agents compose from retrieved rows and the mock provider returns that composition. The model rewrites register; it does not supply facts. The engineering is in the memory layer — provenance, confidence, verification, consent.
How do you stop it hallucinating a medication?
Three mechanisms. Extraction is lexicon-anchored, so a drug name only exists if it matches a known drug. The context block carries provenance inline, so an unverified reading is labelled in the text the model sees. And the mock provider does not generate at all — it returns a draft assembled from rows.
Why 0.85 and 0.60 — did you tune those?
They are reasoned defaults, not fitted parameters, and they are overridable by environment variable in one place. 0.85 is where the extraction stops being reliable enough to trust unattended on the seeded corpus; 0.60 marks readings that are visibly degraded. With a real annotated corpus you would fit them per field. The architecture assumes they will change — that is why they are not scattered through the code.
Why not use a proper embedding model?
Two reasons. It must run offline with no key on a judge's laptop; and character-shingle hashing is genuinely better on OCR noise than a sentence transformer without fine-tuning, because Amlodipme and Amlodipine share 4-grams. Swapping it is one function, embed().
What happens when the pharmacist is wrong?
The original OCR reading and its confidence remain in the record, so a correction is reviewable rather than final. The correction is attributed and timestamped. There is no un-verify action yet — that is on the roadmap as a supervisory review step, which is the honest answer.
Is this HIPAA / DISHA compliant?
No, and it does not claim to be. It implements the architectural preconditions — patient-level authorization, granular consent, complete audit logging, provenance on every fact — but compliance requires encryption at rest, key management, a retention policy, breach procedures and certification. Those are deployment concerns, not a hackathon build.
Why SQLite?
Zero setup, real relational integrity, one file to reset between demos. It is a SQLAlchemy URL away from Postgres, and nothing in the code depends on SQLite specifically.
What if the elderly patient can't use it at all?
That is why guardians are first-class, voice input exists, and the patient dashboard runs at a larger type scale with plain language. The realistic primary user is the guardian or the caregiver — the design assumes that rather than pretending otherwise.
How does a doctor get the record without the patient sending it?
Doctor routing. When a document names a prescriber, the system matches them against the provider directory and creates an assignment if they are registered and consent allows. If they are not registered, an external provider record preserves the name — an account is never fabricated.
What is the hardest part you built?
Making approximate drug matching lower its own confidence honestly. It is easy to fuzzy-match Amlod!pine to Amlodipine and report it as found. Getting it to say "I think this is Amlodipine, but I'm only 54% sure, and that's below the line so a human must confirm" is the difference between a demo and something that could be trusted near a patient.
30

Limits, honestly stated

Naming these before a judge does costs nothing and buys credibility.

  • Rule-based extraction has a ceiling. A 35-drug lexicon covers common Indian geriatric prescribing and nothing else. A drug outside it is invisible. Production needs a full drug database and a trained NER model.
  • No encryption at rest. The SQLite file and uploaded documents are plaintext on disk. Non-negotiable before real patient data.
  • Thresholds are reasoned, not fitted. They need a properly annotated corpus and per-field calibration.
  • Handwriting recognition is only as good as Tesseract. A production system would use a trained handwriting model such as TrOCR — the engine interface already accommodates one.
  • No verification appeal path. A pharmacist's decision stands; the original is preserved but there is no supervisory review.
  • Single-node, single-tenant. No multi-facility isolation, no horizontal scale story.
  • Consent is binary per scope. No time-limited grants, no one-off emergency break-glass with automatic expiry.

Roadmap, in dependency order

  1. Encryption at rest plus key management — everything else is blocked behind this for real data.
  2. Full drug database (RxNorm or CDSCO) replacing the lexicon, with interaction checking.
  3. Trained handwriting model behind the existing HandwritingOCR interface.
  4. Per-field threshold calibration from an annotated corpus.
  5. Time-limited and break-glass consent with automatic expiry.
  6. ABDM / ABHA integration so the memory layer federates with India's national health ID rather than competing with it.
  7. Native mobile with offline capture for caregivers in low-connectivity facilities.

The seeded dataset

Three fictional patients with full longitudinal histories. Critically, the seeder does not insert OCR results — it renders document images with Pillow and pushes them through the real ingestion pipeline, so the seeded confidence scores are genuinely produced by the same code that handles a live upload.
